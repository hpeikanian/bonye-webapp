# تغییرات لازم بنیه برای نسخه ۰٫۴٫۰

کد کلاینت اندروید و وب آماده است؛ این سند به معنی اعمال تغییرات روی سرور نیست. قرارداد قبلی ۵۳٫۲٫۲ فهرست مرجع و عکس پت ندارد. وزن در قرارداد قبلی number است؛ مقدار اعشاری باید در PHP و دیتابیس هم حفظ شود.

## فهرست‌های مرجع یکپارچه

افزودن GET /totallsystem/api/v1/pet-reference?species=dog|cat با احراز هویت معمول اپ:

```json
{"data":{"revision":1,"species":"dog","breeds":[{"code":"golden_retriever","name_fa":"گلدن رتریور","name_en":"Golden Retriever"}],"conditions":[{"code":"diabetes","name_fa":"دیابت","name_en":"Diabetes"}]},"meta":{"api_version":"1"}}
```

مثال بالا فقط نمونه قرارداد است، نه فهرست کامل. breeds و conditions بدون pagination بازگردند تا همه گزینه‌های فعال قابل انتخاب باشند. نژادهای سگ را از فهرست‌های مرجع FCI و AKC و گربه را از CFA/TICA/FIFe با بازبینی، منبع، نسخه و تاریخ دریافت وارد کنید؛ نام‌های مترادف در یک کد پایدار ادغام شوند. «دورگه» و «نامشخص» گزینه‌های مدیریت‌شده داشته باشند. جامع‌بودن را با شمارش و تطبیق با منابع اعلام‌شده تست کنید؛ فهرست کوتاه نمونه یا مدل زبانی جایگزین کامل‌بودن نیست. شرایط شامل بیماری‌ها و نیز حساسیت، بارداری/شیردهی و سایر شرایط تغذیه‌ای است؛ از نظر دامپزشکی و نوع حیوان بازبینی شود.

پاسخ پرونده پت علاوه بر breed code، فیلدهای breed_name_fa و breed_name_en داشته باشد تا نام خوانا در پروفایل نمایش داده شود.

همین مرجع در فرم‌های نرم‌افزار، سایت و اپ استفاده شود. کاربر امکان ثبت آزاد یا ایجاد نژاد/بیماری ندارد؛ مدیر با مسیر کنترل‌شده مرجع را مدیریت می‌کند. کلاینت breed را به صورت code و special_conditions را به صورت آرایه code ارسال می‌کند. سرور اعتبار code و تعلق آن به species را در POST/PATCH /pets کنترل کند. یک condition برای نوع نامرتبط پذیرفته نشود.

در دیتابیس جدول مرجع با code یکتا، species، نام فارسی/انگلیسی، وضعیت و منبع لازم است. رکوردهای موجود متنی با مهاجرت کنترل‌شده به مرجع نگاشت شوند؛ موارد مبهم گزارش شوند و بدون بررسی دور ریخته نشوند. گزارش بر مبنای شناسه/کد پایدار باشد، نه متن ترجمه‌شده. اگر نوع پت تغییر کند، نژاد و شرایط ناسازگار باید پاک/بازانتخاب شوند.

تا آماده‌شدن این API، اپ فهرست را غیرفعال و پیام روشن نشان می‌دهد؛ ویرایش سایر مشخصات و ساخت پرونده بدون نژاد/شرایط همچنان ممکن است. داده قدیمی هنگام ویرایش حفظ می‌شود. اپ هیچ فهرست کوتاهی را به عنوان «همه نژادها» جا نمی‌زند.

## وزن اعشاری

ستون وزن و تاریخچه از نوع DECIMAL(6,3) یا معادل دقیق باشد. از intval، cast int و ورودی فقط عدد صحیح پرهیز شود. PHP مقدار 4.25 را number دریافت و ذخیره کند؛ بازه معتبر 0 < weight_kg <= 200 است. محاسبه جیره و گزارش باید از مقدار کامل استفاده کند. کلاینت ارقام فارسی/عربی و جداکننده‌های . ، , و ٫ را به اعشار تبدیل می‌کند؛ جداکننده هزارگان در فیلد وزن مجاز نیست.

## عکس پت

افزودن PUT /totallsystem/api/v1/pets/{id}/photo با access token و Idempotency-Key؛ فقط مالک پت اجازه داشته باشد. ورودی:

```json
{"content_type":"image/jpeg","image_base64":"..."}
```

پاسخ استاندارد: `{"data":{"photo_url":"https://bonye.pet/.../photo.jpg"},"meta":{"api_version":"1"}}`. همان photo_url در GET /pets و GET /pets/{id} بیاید. تصویر در پرونده نرم‌افزار و سایت نیز نمایش داده شود.

کلاینت فایل JPG/PNG/WebP تا ۱۵ MiB را انتخاب می‌کند؛ عکس‌هایی با بیش از ۴۰ میلیون پیکسل رد می‌شوند تا حافظه بیش از حد مصرف نشود. عکس به JPEG با ضلع بزرگ حداکثر ۱۰۲۴ و حجم حداکثر ۳۰۰ KiB تبدیل می‌شود؛ جهت EXIF اعمال و سپس EXIF/GPS حذف می‌شود. ارسال base64 حدود ۴۰۰ KiB بدنه ایجاد می‌کند. HEIC در این نسخه پشتیبانی نمی‌شود؛ کاربر JPG/PNG انتخاب کند. کلاینت عکس را فقط بعد از پاسخ موفق سرور نمایش می‌دهد.

سرور مستقل از کلاینت MIME واقعی، دیکد امن، سقف حجم و ابعاد را کنترل و دوباره encode کند؛ base64 تا سقف حدود ۴۱۰ کیلوبایت، حجم باینری <=307200 و ضلع <=1024. نام فایل تصادفی/قابل‌اعتماد باشد؛ هیچ نام/مسیر ارسالی مشتری استفاده نشود. پس از ذخیره اتمیک و ثبت موفق دیتابیس، عکس قبلی همان پت حذف شود؛ شکست نباید عکس قبلی را حذف کند. URL جدید با cache-busting یا نام محتوایی تولید شود. احراز مالکیت GET/PUT، جلوگیری از SVG/فایل اجرایی و عدم ثبت عکس/base64/token در لاگ لازم است. سیاست دسترسی عکس بر اساس حریم خصوصی تعیین شود؛ اگر URL عمومی است، این تصمیم روشن باشد.

خطاها با JSON استاندارد، status مناسب و request_id بازگردند. نبود endpoint نباید با موفقیت صوری یا ذخیره صرفاً محلی پوشانده شود.

## باشگاه

پاسخ فعلی باشگاه استفاده می‌شود؛ نمایش نام و شماره عضو از /me است. برای نوار واقعی پیشرفت سطح، در tier فیلد next_threshold عدد مثبت اضافه شود. در نبود آن نوار ساختگی نشان داده نمی‌شود. هدیه تولد، ماموریت و پیشنهاد ویژه فقط با API و قوانین واقعی قابل پیاده‌سازی‌اند؛ این نسخه امتیاز، جایزه یا تخفیف خیالی تولید نمی‌کند.
