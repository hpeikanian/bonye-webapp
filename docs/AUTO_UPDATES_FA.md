# فعال‌سازی یک‌باره انتشار مشترک bonYe!

کد مشترک در `hpeikanian/bonyeapp` است. گردش کار `Build and publish Android and web together` در مخزن `hpeikanian/bonye-webapp` هر دو خروجی را از یک نسخه سورس می‌سازد و روی `https://bonye.pet/app/` منتشر می‌کند. فولدرها و مخزن‌ها جدا می‌مانند. تغییرات Android main با بررسی زمان‌بندی‌شده هر پنج دقیقه شناسایی می‌شوند؛ GitHub ممکن است اجرای زمان‌بندی‌شده را با تأخیر شروع کند. در هر زمان می‌توان Run workflow را هم زد. push وب مستقیماً ساخت مشترک را شروع می‌کند. اجرای زمان‌بندی‌شده بدون تغییر سورس، build نمی‌کند.

## ۱. حساب FTP محدود

در cPanel یک حساب FTP بسازید که Directory آن دقیقاً پوشه واقعی `public_html/app` باشد. حساب اصلی هاست را استفاده نکنید. بعد از ورود با آن حساب، ریشه `/` باید فقط محتویات app را نشان بدهد. FTPS صریح با TLS و پورت ۲۱ باید فعال باشد. نام FTP host باید با گواهی TLS سرور مطابقت داشته باشد؛ از نامی که پشتیبانی هاست برای FTPS می‌دهد استفاده کنید. اسکریپت هیچ‌گاه به FTP بدون رمزگذاری یا گواهی نامعتبر برنمی‌گردد.

## ۲. تنظیمات GitHub در مخزن وب

به Settings → Environments بروید و environment با نام `production` بسازید؛ قوانین انتظار برای تأیید را فقط اگر واقعاً می‌خواهید هر انتشار متوقف بماند اضافه کنید. سپس در Settings → Secrets and variables → Actions این Secrets را ثبت کنید (داخل کد یا Issues نفرستید):

| نام Secret | مقدار |
|---|---|
| `BONYE_FTP_HOST` | نام سرور FTPS، بدون https و بدون پورت |
| `BONYE_FTP_USER` | نام کامل کاربر FTP محدود به app |
| `BONYE_FTP_PASSWORD` | رمز همان حساب |
| `BONYE_ANDROID_KEYSTORE_BASE64` | محتوای Base64 کلید امضای فعلی، مطابق بخش بعد |
| `BONYE_SOURCE_TOKEN` | فقط اگر مخزن Android خصوصی است؛ توکن فقط خواندن آن مخزن |

در زبانه Variables همین صفحه:

| نام Variable | مقدار |
|---|---|
| `BONYE_FTP_APP_ONLY` | `true`؛ فقط پس از محدود کردن واقعی حساب به app |
| `BONYE_DEPLOY_ENABLED` | `true`؛ این مقدار انتشار واقعی را فعال می‌کند |
| `BONYE_FTP_PORT` | `21`؛ اختیاری |

بدون فعال کردن BONYE_DEPLOY_ENABLED، push و اجرای دستی فقط build و Artifact تولید می‌کنند و اجرای دوره‌ای خاموش است. فعال‌سازی فقط با ثبت رمزها کامل می‌شود؛ نوشتن فایل workflow به‌تنهایی هاست را متصل نمی‌کند.

## ۳. حفظ امضای اندروید

APKهای فعلی با کلید توسعه موجود امضا شده‌اند. کلید تازه‌ای که GitHub runner خودکار بسازد با آن‌ها سازگار نیست. بنابراین انتشار خودکار تا دریافت **همان کلید موجود** متوقف می‌شود. fingerprint عمومی مورد انتظار:

```
ea2c98d85ab41af5ef356940d6df2a9bc01f3effa415afae4c142a25b592ce19
```

کلید موجود در محیط توسعه `/workspace/toolchains/android-home/debug.keystore` است. صاحب پروژه باید آن فایل را خصوصی دریافت و در محل امن نگه دارد؛ فایل کلید یا Base64 آن را داخل ریپوزیتوری، Downloads عمومی یا چت منتشر نکنید. در Windows PowerShell برای کپی Base64 فایل دانلودشده به Clipboard:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path '.\debug.keystore'))) | Set-Clipboard
```

Clipboard را مستقیماً در Secret گیت‌هاب BONYE_ANDROID_KEYSTORE_BASE64 وارد کنید، سپس پاک کنید. این کلید توسعه است، نه کلید انتشار فروشگاهی؛ مهاجرت آینده به کلید فروشگاهی نیازمند برنامه جدا برای حفظ سازگاری نصب است. workflow کلید را فقط در runner موقت با permission 600 بازسازی می‌کند، fingerprint را بررسی و در پایان حذف می‌کند. کلید در Artifact قرار نمی‌گیرد. Artifact اندروید workflow بررسی در مخزن Android، بدون کلید موجود، صرفاً آزمایشی CI است؛ برای آپدیت کاربران از خروجی انتشار امضاشده استفاده شود.

## ۴. اولین انتشار و استفاده

در Actions مخزن وب، گردش کار `Build and publish Android and web together` را Run workflow کنید. هر دو خروجی تست می‌شوند؛ APK، package، نسخه و امضا پیش از انتشار بررسی می‌شوند. assets و APK پیش از فایل‌های ورودی و manifest آپدیت منتقل می‌شوند. هر فایل ابتدا با نام موقت آپلود و بعد rename می‌شود؛ دانلود ناقص به نام APK نهایی منتشر نمی‌شود. فایل‌های قدیمی و خریدها حذف نمی‌شوند. حساب FTP محدود اجازه تغییر WordPress یا نرم‌افزار اصلی را ندارد. در آخر نسخه سورس، manifest و اندازه APK از HTTPS خوانده و بررسی می‌شوند. این بررسی، اندازه دانلود را تأیید می‌کند؛ تست نصب روی دستگاه و تست Safari واقعی همچنان لازم است.

اندروید **۰.۲.۳+۶** باید یک بار روی نسخه فعلی نصب شود تا قابلیت بررسی آپدیت اضافه شود. سپس هنگام شروع و برگشت به اپ (با فاصله حداقل یک ساعت)، نسخه بررسی می‌شود. از «حساب من ← به‌روزرسانی اپ» بررسی فوری ممکن است. دریافت فایل و تأیید نصب با کاربر است؛ نصب پنهانی انجام نمی‌شود. اطلاعات حساب برای بررسی نسخه فرستاده نمی‌شوند. آدرس manifest و APK فقط دامنه HTTPS بنیه است. Android هنگام نصب سازگاری امضای APK را بررسی می‌کند؛ دانلود داخل مرورگر است و خود Flutter فایل را دانلود یا SHA256 آن را دوباره محاسبه نمی‌کند.

وب‌اپ نسخه جدید را با Service Worker پس از بسته‌شدن تب‌های قبلی دریافت می‌کند؛ پرداخت فعال با refresh اجباری قطع نمی‌شود. manifest آپدیت و APK داخل کش آفلاین پوسته وب قرار نمی‌گیرند. CDN/هاست باید Cache-Control فایل‌های index، bootstrap، sw، source-revision و android-update را رعایت کند.

## توسعه بعدی و خطا

هر تغییر قابل انتشار در اپ باید شماره `version` در pubspec.yaml، به‌ویژه عدد پس از + را افزایش دهد. سپس commit و push سورس؛ انتقال دستی ZIP هر بار لازم نیست. تغییرات پادکست و محتوای API همچنان از پنل مدیریت دریافت می‌شوند. اصلاح افزونه WordPress یا ERP مسیر انتشار مستقل دارد.

انتشار FTPS برای تک‌تک فایل‌ها rename دارد؛ تراکنش اتمی برای کل فولدر نیست. در قطع اتصال، فایل‌های منتقل‌نشده ممکن است هنوز نسخه قبلی باشند. کاربر فعال معمولاً از پوسته کش‌شده استفاده می‌کند؛ انتشار ناموفق را اعلام نکنید و workflow را دوباره اجرا کنید. اجرای همزمان انتشارها سری شده است. برای توقف انتشار خودکار BONYE_DEPLOY_ENABLED را false کنید. نسخه‌های APK نگه داشته می‌شوند و حذف قدیمی‌ها عملی جداست. شماره نسخه عمومی اندروید هیچ‌گاه به عقب برنمی‌گردد.

## وضعیت این پیاده‌سازی

کد، تست‌های بررسی نسخه، تست‌های ترتیب و قطع انتقال FTPS، build اندروید و وب به صورت محلی قابل بررسی هستند. اتصال به هاست، ثبت Secrets، اجرای موفق workflow روی GitHub و نصب روی گوشی واقعی بدون دسترسی مربوطه قابل تأیید نیستند. رمزها در محیط فعلی ثبت نشده‌اند؛ انتشار زنده هنوز انجام نشده است.
